# 2.2 컨테이너 직접 다뤄 보기

**Dockerfile 작성 → 빌드 → 실행**, 이 세 단계가 컨테이너 작업의 기본입니다.

> **책은 `docker` 명령으로 설명하지만, 이 노트는 `podman` 을 씁니다.** Docker Desktop은 일정 규모 이상의 기업에서 유료 구독이 필요한 반면 Podman은 그런 조건이 없어서, 회사에서 그대로 쓸 수 있는 쪽을 택했습니다.
>
> **명령어 체계는 같습니다.** 아래 모든 명령은 `podman` 을 `docker` 로 바꿔도 똑같이 동작합니다. 반대로 인터넷의 `docker` 예제를 볼 때는 `podman` 으로 바꿔 읽으면 됩니다.

## 첫 번째 컨테이너 실행하기

```bash
podman run docker.io/library/busybox echo "Hello world"
```

이 한 줄에서 벌어지는 일입니다.

1. 로컬에 `busybox` 이미지가 있는지 확인 → 없음
2. Docker Hub에서 `busybox` 이미지를 내려받음(pull)
3. 그 이미지로 컨테이너를 만들고 실행
4. `echo "Hello world"` 명령 실행 후 컨테이너 종료

> **왜 `docker.io/library/` 를 붙이나요?** Docker와 달리 **Podman은 이름만 쓰면 "어느 레지스트리에서 받을까요?"를 되묻습니다.** 그래서 이 노트는 전체 주소를 적습니다.

> **busybox란?** 리눅스 기본 명령어(`ls`, `cat`, `echo` 등) 수백 개를 하나의 작은 실행 파일에 몰아넣은 도구입니다. 크기가 1MB 남짓이라 테스트용으로 자주 쓰입니다.

### 태그(Tag) 지정하기

```bash
podman run docker.io/library/busybox:1.36 echo "Hello"
```

`이미지이름:태그` 형식입니다. 태그를 생략하면 `latest`가 붙습니다.

> **`latest`를 쓰지 마세요.**
> `latest`는 "최신"이라는 뜻이 아니라 그냥 **기본 태그 이름**일 뿐입니다. 오늘의 `latest`와 내일의 `latest`가 다른 이미지일 수 있어서, 어제는 되던 게 오늘 안 되는 사고가 납니다. 실무에서는 항상 `1.36` 처럼 **명확한 버전**을 지정합니다.

## 이미지로 만들 앱 준비하기

이미지 안에 넣을 프로그램이 있어야 합니다. 요청이 오면 **자기가 어느 컨테이너에서 돌고 있는지** 알려 주는 Node.js 웹 서버를 씁니다. 뒤 장에서도 계속 쓰게 될 앱입니다.

빈 폴더를 하나 만들고, 그 안에 아래 두 파일(`app.js`, `Dockerfile`)을 만듭니다.

**app.js**

```javascript
const http = require('http');
const os = require('os');

console.log("Kiada 앱이 시작되었습니다...");

const handler = function (request, response) {
  response.writeHead(200);
  response.end("Kiada 인사드립니다! 호스트명: " + os.hostname() + "\n");
};

http.createServer(handler).listen(8080);
```

핵심은 **`os.hostname()`** 입니다. 컨테이너의 호스트명을 그대로 출력하기 때문에, 나중에 같은 앱을 여러 개 띄웠을 때 **어느 것이 응답했는지** 눈으로 구분할 수 있습니다.

## Dockerfile 작성하기

**Dockerfile** 은 "이미지를 이렇게 만들어라"라고 적은 조리법입니다. `app.js` 와 **같은 폴더**에 확장자 없이 `Dockerfile` 이라는 이름으로 저장합니다.

```dockerfile
FROM docker.io/library/node:20-alpine
COPY app.js /app.js
ENTRYPOINT ["node", "/app.js"]
```

| 명령어 | 의미 |
| :--- | :--- |
| `FROM` | 어떤 베이스 이미지에서 출발할지 |
| `COPY` | 내 컴퓨터의 파일을 이미지 안으로 복사 |
| `ENTRYPOINT` | 컨테이너가 시작될 때 실행할 명령 |

> **`-alpine` 태그**는 초경량 리눅스를 베이스로 쓴다는 뜻입니다. `node:20`은 약 1GB, `node:20-alpine`은 약 130MB입니다.

> **`ENTRYPOINT` 와 `CMD`.** 둘 다 시작 명령을 정하지만, `ENTRYPOINT`는 고정이고 `CMD`는 덮어쓸 수 있는 기본값입니다. **파드 YAML의 `command`·`args`가 바로 이 둘을 덮어쓰는 설정입니다.** (4장에서 다룹니다)

## 이미지 빌드하기

```bash
podman build -t kiada:0.1 .
```

* `-t kiada:0.1` : 만들어질 이미지의 이름과 태그
* `.` : Dockerfile이 있는 위치(현재 디렉터리)

빌드가 끝나면 확인합니다.

```bash
podman images kiada
# REPOSITORY       TAG   IMAGE ID      CREATED                 SIZE
# localhost/kiada  0.1   b94539f9f5b1  Less than a second ago  138 MB
```

> **`localhost/` 는 왜 붙나요?** Podman은 방금 내가 만든 이미지에 "아직 어느 레지스트리에도 올라가지 않았다"는 뜻으로 `localhost/` 를 붙입니다. 실행할 때는 `podman run kiada:0.1` 처럼 짧게 써도 로컬을 먼저 뒤지므로 그대로 동작합니다.


## 컨테이너 실행하기

이제 이미지를 실제로 띄웁니다.

```bash
podman run --name kiada-container -p 8080:8080 -d kiada:0.1
```

| 옵션 | 의미 |
| :--- | :--- |
| `--name` | 컨테이너에 이름 붙이기 |
| `-p 8080:8080` | **호스트 8080 포트를 컨테이너 8080 포트에 연결** |
| `-d` | 백그라운드(detached)로 실행 |

**포트 매핑이 핵심입니다.** 컨테이너는 격리되어 있어서 밖에서 바로 접근할 수 없습니다. `-p 호스트포트:컨테이너포트` 로 통로를 뚫어 줘야 합니다.

이제 접속해 봅니다.

```bash
curl localhost:8080
# Kiada 인사드립니다! 호스트명: 5c74097f9454
```

브라우저에서 `http://localhost:8080` 으로 들어가도 됩니다.

> **Windows에서 접속이 안 된다면** `podman machine` 이 켜져 있는지부터 확인하세요. 컨테이너는 Windows가 아니라 **WSL2 안의 리눅스 VM에서** 돌고 있고, `-p` 로 연 포트는 Podman이 Windows까지 이어 줍니다. VM이 꺼져 있으면 이 통로 자체가 없습니다.

확인이 끝났으면 정리합니다. `-d` 로 띄운 컨테이너는 **끄기 전까지 8080 포트를 계속 붙잡고 있습니다.**

```bash
podman ps                     # 실행 중인 컨테이너 확인
podman rm -f kiada-container  # 정지 + 삭제
```

## 쿠버네티스에서 실행해 보기

같은 이미지를 kind 클러스터에서도 띄워 봅니다. 2장의 마지막 확인이자, 쿠버네티스로 넘어가는 다리입니다.

### 클러스터에 이미지 넣기

원래 쿠버네티스는 **레지스트리(Docker Hub 등)에 올라간 이미지**를 받아서 실행합니다. 하지만 학습 중에 이미지를 고칠 때마다 올리는 것은 번거롭습니다. **kind는 내 PC의 이미지를 노드 안으로 바로 복사**해 주는 기능이 있어서, 레지스트리를 건너뛸 수 있습니다.

```powershell
podman save -o kiada.tar localhost/kiada:0.1     # 이미지를 파일로 저장
kind load image-archive kiada.tar --name kia     # 노드 안으로 복사
```

노드 안에 들어갔는지는 노드에서 직접 확인합니다. 노드에는 `podman`이 없으므로 `crictl`을 씁니다.

```powershell
podman exec kia-control-plane crictl images | Select-String kiada
# localhost/kiada   0.1   b94539f9f5b19   138MB
```

> **`kind load docker-image` 는 Podman 환경에서 실패할 수 있습니다.** 더 간단해 보이는
> `kind load docker-image localhost/kiada:0.1 --name kia` 는 이미지가 분명히 있는데도
> `ERROR: image: "localhost/kiada:0.1" not present locally` 를 냅니다(kind 0.32 + podman 5.8.3에서 확인).
> **위의 `podman save` + `image-archive` 방식은 문제없이 동작합니다.**

이렇게 넣은 이미지로 파드를 띄울 때는 **`imagePullPolicy: Never`** 를 반드시 지정합니다. 그러지 않으면 쿠버네티스가 `localhost/kiada:0.1` 을 인터넷에서 받으려다 실패합니다.

```powershell
kubectl run kiada --image=localhost/kiada:0.1 --image-pull-policy=Never --port=8080
kubectl get pod kiada
# NAME    READY   STATUS    RESTARTS   AGE
# kiada   1/1     Running   0          5s
```

파드 안의 앱에 접속하려면 통로를 뚫습니다. `podman run -p` 에 해당하는 쿠버네티스 명령입니다.

```powershell
kubectl port-forward pod/kiada 8080:8080
```

다른 창에서 접속해 보면 **호스트명이 파드 이름으로** 나옵니다.

```powershell
curl localhost:8080
# Kiada 인사드립니다! 호스트명: kiada
```

> **아까와 비교해 보세요.** `podman run` 으로 띄웠을 때는 호스트명이 컨테이너 ID(`5c74097f9454`)였는데, 파드에서는 **파드 이름 `kiada`** 가 나옵니다. 쿠버네티스가 컨테이너의 호스트명을 파드 이름으로 맞춰 주기 때문입니다. 나중에 파드를 여러 개 띄우면 이 값으로 **어느 파드가 응답했는지** 구분하게 됩니다.

```powershell
kubectl delete pod kiada    # 확인이 끝났으면 정리
```

## 요약 및 비유

| 명령 | 요리 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **Dockerfile** | 레시피를 적은 종이 | 이미지 빌드 절차 정의 |
| **podman build** | 레시피대로 밀키트 제작 | 이미지 생성 |
| **podman run** | 밀키트를 조리해서 먹기 | 컨테이너 실행 |
| **podman pull** | 마트에서 밀키트 구입 | 레지스트리에서 이미지 내려받기 |
| **kind load image-archive** | 마트를 안 거치고 옆집에 직접 배달 | 로컬 이미지를 클러스터 노드에 직접 복사 |
| **-p 8080:8080** | 가게 문을 열어 손님을 받음 | 호스트 포트를 컨테이너에 연결 |

## 결론

* `Dockerfile` 작성 → `podman build` → `podman run` 이 컨테이너 작업의 기본 흐름입니다.
* 쿠버네티스는 보통 레지스트리에서 이미지를 받지만, 학습 환경에서는 **`podman save` + `kind load image-archive`** 로 클러스터에 직접 넣을 수 있습니다. 이때 파드에는 **`imagePullPolicy: Never`** 가 필요합니다.
* **`podman`과 `docker`는 명령어가 같습니다.** 도구를 바꿔도 배운 것이 그대로 쓰입니다.
* 이미지 태그는 **`latest` 대신 명확한 버전**을 쓰는 습관을 들이세요.
* 실무에서 **빌드와 푸시는 CI가 대신합니다.** 쿠버네티스를 쓰는 쪽에서 직접 정하는 것은 **어떤 이미지 이름·태그를 참조할지**입니다.
* 포트 매핑(`-p`) 없이는 컨테이너 안의 서비스에 접근할 수 없습니다.

## 공식 문서 업데이트 (2026년 8월 기준)

### 1) 여기서 배운 명령은 계속 유효합니다

2.1절에서 "쿠버네티스에서 Docker는 런타임이 아니다"라고 했지만, **이 절의 내용은 그대로 쓰면 됩니다.** 쿠버네티스가 걷어낸 것은 *노드에서 컨테이너를 돌리는 런타임으로서의* Docker이고, **이미지를 만들고 로컬에서 테스트하는 도구**로서는 Docker든 Podman이든 아무 문제가 없습니다. 결과물이 OCI 표준 이미지라 쿠버네티스가 그대로 받아 실행합니다.

### 2) 쿠버네티스 노드 안에서는 `docker`도 `podman`도 없습니다

로컬에서는 `podman ps`를 쓰지만, 쿠버네티스 노드에 들어가면 둘 다 설치되어 있지 않습니다. 노드는 CRI 규격의 런타임(containerd 등)만 갖고 있어서 **`crictl`** 을 씁니다. (2.1절 참고)

### 3) 이미지 보안 스캔이 기본이 되었습니다

공급망 공격이 늘면서, 요즘은 이미지를 만들면 취약점을 검사하는 것이 당연해졌습니다.

```bash
trivy image kiada:0.1    # 가장 널리 쓰이는 오픈소스 스캐너
```

Podman에는 Docker의 `docker scout` 같은 내장 스캐너가 없어서 **`trivy`** 를 따로 씁니다. 베이스 이미지를 `alpine`이나 `distroless`처럼 작은 것으로 고르면 취약점 개수 자체가 크게 줄어듭니다.
