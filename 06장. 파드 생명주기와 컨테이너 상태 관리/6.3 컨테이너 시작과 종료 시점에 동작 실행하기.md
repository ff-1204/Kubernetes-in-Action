# 6.3 컨테이너 시작과 종료 시점에 동작 실행하기

컨테이너가 **막 시작한 순간**과 **곧 종료될 순간**에 원하는 작업을 끼워 넣고 싶을 때가 있습니다. **생명주기 훅(Lifecycle Hook)** 이 그 자리를 만들어 줍니다.

## 훅은 두 개뿐입니다

| 훅 | 실행 시점 |
| :--- | :--- |
| **`postStart`** | 컨테이너가 만들어진 **직후** |
| **`preStop`** | 컨테이너가 종료되기 **직전** |

```mermaid
graph LR
    C["컨테이너 생성"] --> PS["postStart 훅"]
    PS --> R["실행 중 (Running)"]
    R --> PRE["preStop 훅"]
    PRE --> T["SIGTERM → 종료"]
```

> 5.2절의 **초기화 컨테이너**와 헷갈리기 쉽습니다. init 컨테이너는 **앱 컨테이너가 뜨기 전에 별도 컨테이너로** 실행되지만, `postStart`는 **앱 컨테이너 안에서 앱과 동시에** 실행됩니다.

## 핸들러 세 가지

훅이 실제로 무엇을 할지 정하는 방식입니다.

### 1) `exec` — 컨테이너 안에서 명령 실행

```yaml
lifecycle:
  postStart:
    exec:
      command: ["/bin/sh", "-c", "echo 시작됨 >> /var/log/hook.log"]
```

### 2) `httpGet` — HTTP 요청 전송

```yaml
lifecycle:
  preStop:
    httpGet:
      path: /shutdown
      port: 8080
```

이 요청은 **컨테이너 안이 아니라 kubelet이 대신** 보냅니다.

### 3) `sleep` — 그냥 기다리기

```yaml
lifecycle:
  preStop:
    sleep:
      seconds: 5
```

> 예전에는 `exec`로 `["sh", "-c", "sleep 5"]`를 실행해야 했습니다. 그러려면 **컨테이너 이미지 안에 셸이 있어야** 해서, distroless 이미지에서는 쓸 수 없었습니다. 지금은 `sleep` 핸들러가 정식 기능이라 이 문제가 사라졌습니다.

## `postStart` 훅

### 동작 특성

* 컨테이너의 **`ENTRYPOINT`와 동시에** 시작됩니다. 순서가 보장되지 않습니다.
* **앱보다 먼저 끝날 수도, 나중에 끝날 수도** 있습니다.
* 훅이 끝날 때까지 **컨테이너 상태가 `Running`으로 넘어가지 않습니다.**
* 훅이 실패하면 **컨테이너가 죽고 재시작 정책에 따라 다시 뜹니다.**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kiada-poststart
spec:
  containers:
    - name: kiada
      image: luksa/kiada:0.1
      lifecycle:
        postStart:
          exec:
            command:
              - /bin/sh
              - -c
              - "echo $(date) 컨테이너 시작 >> /var/log/lifecycle.log"
```

### 주의할 점

**`postStart`로 앱을 초기화하려 하면 안 됩니다.** 앱과 동시에 실행되므로 "앱이 다 뜬 다음"이 보장되지 않습니다.

* 준비 작업이 **앱보다 먼저** 끝나야 한다면 → **초기화 컨테이너**(5.2절)
* 앱과 **계속 함께** 돌아야 한다면 → **사이드카**
* `postStart`는 "알림 보내기, 로그 남기기" 정도의 **가벼운 부수 작업**에 적합합니다

또한 훅이 오래 걸리면 그동안 컨테이너가 `Running`이 안 되고, **프로브도 시작되지 않습니다.** 반드시 가볍게 만드세요.

## `preStop` 훅

### 동작 특성

* 컨테이너 종료가 결정되면 **`SIGTERM`보다 먼저** 실행됩니다.
* 훅이 끝날 때까지 **`SIGTERM` 전송이 미뤄집니다.**
* **종료 유예 시간(`terminationGracePeriodSeconds`)이 훅 실행 시간부터 흘러갑니다.**
* 삭제뿐 아니라 **라이브니스 실패, 노드 축출, 선점** 등으로 종료될 때도 실행됩니다.

```yaml
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: kiada
      image: luksa/kiada:0.1
      lifecycle:
        preStop:
          sleep:
            seconds: 5
```

### 유예 시간을 나눠 쓴다는 점이 핵심입니다

훅 시간과 앱 종료 시간이 **같은 예산을 나눠 씁니다.**

```mermaid
graph LR
    A["종료 결정<br/>유예 60초 시작"] --> B["preStop 훅<br/>55초 소요"]
    B --> C["SIGTERM 전송<br/>앱이 10초 필요"]
    C --> D["65초 > 60초<br/>SIGKILL 강제 종료 ❌"]
```

> `preStop`이 55초를 쓰면 앱에는 5초밖에 안 남습니다. **훅 시간 + 앱 종료 시간 < `terminationGracePeriodSeconds`** 가 되도록 잡아야 합니다.

### 무중단 배포의 핵심: `preStop` + `sleep`

5.2절에서 다룬 **경쟁 상태** 문제의 정식 해법입니다.

파드가 종료될 때 두 가지가 **동시에** 일어납니다.

1. 서비스 엔드포인트에서 파드 제거 → 모든 노드의 `kube-proxy`에 전파 (**시간이 걸림**)
2. kubelet이 종료 절차 시작

전파가 끝나기 전에 앱이 먼저 죽으면, 아직 옛 정보를 가진 노드가 이 파드로 요청을 보내고 **502 오류**가 납니다.

```yaml
lifecycle:
  preStop:
    sleep:
      seconds: 5      # 전파될 시간을 벌어 준다
```

**앱 코드를 한 줄도 안 고치고** 배포 중 오류를 없앨 수 있는, 실무에서 매우 자주 쓰는 패턴입니다.

## 훅을 쓸 때 꼭 알아야 할 것들

### 최소 한 번(at-least-once) 전달

훅은 **두 번 이상 실행될 수 있습니다.** kubelet이 훅 실행 도중 재시작되는 경우 등입니다. 따라서 훅은 **몇 번 실행해도 결과가 같도록(멱등하게)** 만들어야 합니다.

### 훅 실패 = 컨테이너 종료

훅이 실패하면 컨테이너가 죽습니다. 이벤트로 확인합니다.

```bash
kubectl describe pod kiada-poststart
```

```
Events:
  Warning  FailedPostStartHook  Exec lifecycle hook ... failed - exit status 1
  Warning  FailedPreStopHook    ...
```

### 훅의 로그는 파드 로그에 안 나옵니다

가장 헷갈리는 부분입니다. `kubectl logs`에는 **훅 출력이 표시되지 않습니다.**

```bash
kubectl describe pod 파드이름          # 실패 여부는 Events 에서
```

훅 안에서 무슨 일이 있었는지 보려면 **직접 파일로 남기고** 꺼내 봐야 합니다.

```yaml
postStart:
  exec:
    command: ["/bin/sh", "-c", "내명령 >> /proc/1/fd/1 2>&1"]   # 앱 표준출력으로 흘려보내기
```

`/proc/1/fd/1`은 1번 프로세스의 표준 출력입니다. 여기에 쓰면 `kubectl logs`에서 보입니다.

### 자원은 컨테이너 몫에서 나갑니다

`exec` 훅은 컨테이너의 cgroup 안에서 실행됩니다. 무거운 명령을 넣으면 **앱의 CPU·메모리 한도를 잡아먹습니다.**

## 훅 vs 다른 방법, 무엇을 쓸까

| 하고 싶은 일 | 알맞은 방법 |
| :--- | :--- |
| 앱 시작 **전에** 반드시 끝나야 하는 준비 | **초기화 컨테이너** (5.2절) |
| 앱과 **계속 함께** 도는 보조 작업 | **사이드카** |
| 컨테이너 시작 시점의 가벼운 알림·기록 | **`postStart` 훅** |
| 종료 직전 정리, 엔드포인트 전파 대기 | **`preStop` 훅** |
| 요청 처리 중단·연결 정리 | **앱에서 `SIGTERM` 처리** |

> **훅이 만능은 아닙니다.** 제대로 된 우아한 종료는 결국 **앱이 `SIGTERM`을 처리**해야 완성됩니다. `preStop`은 그 앞의 시간차를 메우는 보조 수단입니다.

## 요약 및 비유

| 개념 | 근무 교대 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **`postStart` 훅** | 출근하자마자 출근부에 서명 | 컨테이너 생성 직후 실행, `Running` 전이를 막음 |
| **`preStop` 훅** | 퇴근 전 인수인계 | 종료 직전, `SIGTERM`보다 먼저 실행 |
| **`sleep` 핸들러** | "5분만 더 자리 지키기" | 셸 없이도 대기 가능한 정식 핸들러 |
| **유예 시간 공유** | 정해진 퇴근 시각은 하나 | 훅 + 앱 종료가 같은 예산을 나눠 씀 |
| **최소 한 번 전달** | 인수인계를 두 번 할 수도 | 훅은 중복 실행될 수 있으므로 멱등하게 |
| **훅 실패 = 종료** | 서명 못 하면 근무 무효 | 훅이 실패하면 컨테이너가 죽음 |

## 결론

* 훅은 **`postStart`(생성 직후)** 와 **`preStop`(종료 직전)** 둘뿐이며, 핸들러는 `exec` / `httpGet` / `sleep` 세 가지입니다.
* `postStart`는 **앱과 동시에** 실행되므로 순서가 보장되지 않습니다. 순서가 필요하면 **초기화 컨테이너**를 쓰세요.
* `preStop`은 **종료 유예 시간을 앱과 나눠 씁니다.** 훅이 길면 앱이 강제 종료됩니다.
* **`preStop` + `sleep`** 은 배포 중 502 오류를 없애는 실무 필수 패턴입니다.
* 훅은 **중복 실행될 수 있고**, **로그가 `kubectl logs`에 안 나오며**, **실패하면 컨테이너를 죽입니다.**

다음 절에서는 지금까지 배운 조각들을 하나로 이어 **파드의 전체 생명주기**를 정리합니다.

## 공식 문서 업데이트 (2026년 8월 기준)

* **`sleep` 핸들러가 정식 기능**입니다. 1.29에 도입되어 **1.30부터 기본 활성화**되었고, 0초 지정까지 포함해 안정화되었습니다. 책에 나오는 `exec` + `sh -c "sleep 5"` 방식은 이제 **셸 없는 이미지에서도 쓸 수 있는 `sleep` 핸들러로 대체**하는 것이 좋습니다.
* **`stopSignal` 필드**가 추가되었습니다. 컨테이너 종료 시 보낼 신호를 파드 스펙에서 직접 지정할 수 있어, 이미지의 `STOPSIGNAL`을 덮어쓸 수 있습니다. `SIGTERM` 대신 다른 신호를 기대하는 앱에 유용합니다.
