# 5.3 객체 상태와 이벤트 살펴보기

객체가 지금 어떤 상태인지, 무슨 일이 있었는지 읽는 법을 배웁니다. **문제 해결(트러블슈팅)의 기본기**입니다. 앞 절들에서 파드를 직접 만들고 부숴 봤으니, 이제 "왜 그렇게 됐는지" 읽어 낼 차례입니다.

> 원서에서는 API·오브젝트 모델 장(이 저장소의 3장)에 속한 내용이지만, **파드를 다뤄 본 뒤라야 와닿기 때문에** 이 자리로 옮겼습니다. 다루는 대상은 파드만이 아니라 **모든 객체**입니다.

## 노드 객체 뜯어보기

노드는 구조가 풍부해서 공부하기 좋은 객체입니다.

```bash
kubectl get node kiada-worker -o yaml
```

### spec 부분

```yaml
spec:
  podCIDR: 10.244.1.0/24        # 이 노드의 파드에 줄 IP 대역
  taints:                        # 이 노드를 꺼리게 만드는 표시
    - key: node-role.kubernetes.io/control-plane
      effect: NoSchedule
```

**테인트(Taint)** 는 "이 노드에는 아무나 오지 마"라는 표시입니다. 컨트롤 플레인 노드에 기본으로 붙어 있어서, 일반 앱 파드가 배치되지 않습니다.

### status 부분

```yaml
status:
  capacity:                    # 노드의 전체 용량
    cpu: "8"
    memory: 16256000Ki
    pods: "110"
  allocatable:                 # 실제로 파드에 나눠 줄 수 있는 양
    cpu: "7800m"
    memory: 15731200Ki
  nodeInfo:
    kubeletVersion: v1.36.0
    containerRuntimeVersion: containerd://2.0.0
    operatingSystem: linux
    architecture: amd64
```

> **capacity와 allocatable의 차이**
> 노드에는 kubelet, kube-proxy, 운영체제 자체도 돌아갑니다. 그 몫을 떼어 놓은 나머지가 **allocatable**입니다. 스케줄러는 capacity가 아니라 **allocatable을 기준으로** 파드를 배치합니다.

`containerRuntimeVersion`을 보면 **containerd**가 쓰이고 있음을 확인할 수 있습니다. Docker가 아닙니다.

## 컨디션(Conditions): 상태를 읽는 표준 방식

거의 모든 쿠버네티스 객체는 `status.conditions` 배열을 가집니다. **"이 객체가 어떤 조건을 만족하는가"** 를 항목별로 기록한 것입니다.

```yaml
status:
  conditions:
    - type: Ready
      status: "True"
      reason: KubeletReady
      message: kubelet is posting ready status
      lastTransitionTime: "2026-08-19T10:00:00Z"
    - type: MemoryPressure
      status: "False"
      reason: KubeletHasSufficientMemory
    - type: DiskPressure
      status: "False"
    - type: PIDPressure
      status: "False"
```

각 컨디션의 구성 요소입니다.

| 필드 | 의미 |
| :--- | :--- |
| `type` | 어떤 조건인가 (Ready, MemoryPressure 등) |
| `status` | `"True"` / `"False"` / `"Unknown"` — **문자열입니다** |
| `reason` | 기계가 읽는 짧은 이유 코드 |
| `message` | 사람이 읽는 설명 |
| `lastTransitionTime` | 상태가 마지막으로 바뀐 시각 |

> **왜 `status`가 boolean이 아니라 문자열일까요?**
> **`Unknown`** 이라는 세 번째 상태가 필요하기 때문입니다. 노드와 연결이 끊기면 "정상인지 비정상인지 알 수 없는" 상태가 됩니다. true/false만으로는 이를 표현할 수 없습니다.

### 노드의 주요 컨디션

| type | `True`일 때의 의미 |
| :--- | :--- |
| `Ready` | 정상. 파드를 받을 수 있음 |
| `MemoryPressure` | **메모리 부족** |
| `DiskPressure` | **디스크 부족** |
| `PIDPressure` | **프로세스 수가 너무 많음** |
| `NetworkUnavailable` | **네트워크 설정에 문제** |

`Ready`만 `True`가 정상이고, **나머지는 `False`가 정상**입니다. 헷갈리기 쉬우니 주의하세요.

### 파드의 주요 컨디션

| type | 의미 |
| :--- | :--- |
| `PodScheduled` | 노드에 배치되었는가 |
| `Initialized` | init 컨테이너가 모두 끝났는가 |
| `ContainersReady` | 모든 컨테이너가 준비되었는가 |
| `Ready` | 서비스가 트래픽을 보내도 되는가 |

```bash
kubectl get pod kiada -o jsonpath='{.status.conditions}' | jq
```

## 이벤트(Events): 클러스터의 CCTV

**이벤트**는 클러스터에서 벌어진 일을 기록한 별도의 객체입니다. 트러블슈팅에서 가장 먼저 봐야 할 곳입니다.

```bash
kubectl get events
kubectl get events --sort-by=.metadata.creationTimestamp
kubectl events                          # 새로 생긴 전용 명령 (권장)
kubectl events --for pod/kiada          # 특정 객체의 이벤트만
kubectl events -w                       # 실시간 감시
```

또는 `describe`의 맨 아래에서 볼 수 있습니다.

```bash
kubectl describe pod kiada
```

```
Events:
  Type     Reason      Age   From               Message
  ----     ------      ----  ----               -------
  Normal   Scheduled   30s   default-scheduler  Successfully assigned default/kiada to kiada-worker
  Normal   Pulling     29s   kubelet            Pulling image "luksa/kiada:0.1"
  Normal   Pulled      25s   kubelet            Successfully pulled image
  Normal   Created     25s   kubelet            Created container kiada
  Normal   Started     24s   kubelet            Started container kiada
```

### 이벤트 타입

* **Normal**: 정상적인 흐름
* **Warning**: 문제가 있음. **이것부터 확인하세요**

```bash
kubectl get events --field-selector type=Warning
```

### 자주 보게 되는 Warning 이벤트

| Reason | 원인 | 해결 방향 |
| :--- | :--- | :--- |
| `FailedScheduling` | 배치할 노드가 없음 | 자원 부족, 테인트, 노드셀렉터 확인 |
| `ErrImagePull` / `ImagePullBackOff` | 이미지를 못 받음 | 이미지 이름·태그 오타, 레지스트리 인증 확인 |
| `CrashLoopBackOff` | 컨테이너가 계속 죽음 | `kubectl logs --previous`로 앱 오류 확인 |
| `OOMKilled` | 메모리 한도 초과 | `resources.limits.memory` 상향 |
| `Unhealthy` | 프로브 실패 | 프로브 경로·포트·타이밍 확인 |
| `FailedMount` | 볼륨 연결 실패 | PVC 상태, 스토리지클래스 확인 |

> **이벤트는 오래 남지 않습니다.**
> 기본 보존 시간이 **1시간**입니다. 어제 발생한 문제를 오늘 조사하려고 하면 이벤트가 이미 사라지고 없습니다. 그래서 실무에서는 이벤트를 로깅 시스템으로 따로 수집합니다.

## 문제 해결 순서

파드가 안 뜰 때 이 순서로 확인하면 대부분 해결됩니다.

```
1. kubectl get pods
   -> STATUS 열을 확인 (Pending? ImagePullBackOff? CrashLoopBackOff?)

2. kubectl describe pod <이름>
   -> 맨 아래 Events 섹션을 읽음. 원인의 90%가 여기 있음

3. kubectl logs <이름>
   -> 컨테이너가 뜨긴 했다면 앱 로그 확인
   -> 죽었다 살아났다면 kubectl logs <이름> --previous

4. kubectl get events --field-selector type=Warning
   -> 클러스터 전체 경고 확인

5. kubectl exec -it <이름> -- sh
   -> 컨테이너 안에 들어가서 직접 조사
```

### STATUS 값으로 원인 좁히기

| STATUS | 어디를 봐야 하나 |
| :--- | :--- |
| `Pending` | **아직 노드 배치 전.** describe의 Events → 스케줄링 실패 이유 |
| `ContainerCreating` | 이미지 받는 중이거나 볼륨 연결 중. 오래 걸리면 describe |
| `ImagePullBackOff` | 이미지 이름·태그·인증 문제 |
| `CrashLoopBackOff` | **앱이 시작하자마자 죽음.** `logs --previous` |
| `Error` | 컨테이너가 0이 아닌 코드로 종료. `logs` |
| `Running` 인데 `READY 0/1` | **프로브 실패.** describe의 Unhealthy 이벤트 |

**`Running`인데 `READY`가 `0/1`인 상황**은 특히 헷갈립니다. 컨테이너는 돌고 있지만 **레디니스 프로브를 통과하지 못해** 서비스가 트래픽을 안 보내는 상태입니다. 6장에서 자세히 다룹니다.

## 요약 및 비유

| 개념 | 병원 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **spec** | 의사의 처방전 | 원하는 상태 |
| **status** | 현재 환자 상태 차트 | 실제 상태 |
| **conditions** | 체온·혈압 등 항목별 체크 | 조건별 True/False/Unknown |
| **Unknown** | 연락이 안 되어 상태 파악 불가 | 통신 두절 상태 |
| **events** | 진료 기록지 | 클러스터에서 일어난 일의 로그 |
| **Warning 이벤트** | 이상 소견 기록 | 문제 발생 신호 |
| **capacity / allocatable** | 병상 총수 / 실제 배정 가능 병상 | 전체 자원 / 파드에 줄 수 있는 자원 |

## 결론

* **`conditions`** 는 객체 상태를 읽는 표준 방식입니다. `status`가 `"True"/"False"/"Unknown"` 문자열이라는 점을 기억하세요.
* 노드 컨디션은 **`Ready`만 True가 정상**이고 나머지 Pressure 계열은 False가 정상입니다.
* **이벤트가 트러블슈팅의 출발점**입니다. `kubectl describe`의 Events를 읽는 습관을 들이세요.
* 이벤트는 **기본 1시간만 보존**되므로 문제가 생기면 바로 확인해야 합니다.
* `get` → `describe` → `logs` → `events` → `exec` 순서를 몸에 익히면 대부분의 문제를 스스로 풀 수 있습니다.

## 공식 문서 업데이트 (2026년 8월 기준)

### 1) `kubectl events` 전용 명령 (권장)

책에는 `kubectl get events`만 나오지만, 지금은 전용 명령이 있습니다. **시간순으로 정렬되어 나오고** 특정 객체로 필터링하기도 훨씬 쉽습니다.

```bash
kubectl events                        # 시간순 정렬
kubectl events --for pod/kiada        # 특정 파드
kubectl events --types=Warning        # 경고만
kubectl events -w                     # 실시간
```

### 2) 파드 컨디션이 추가되었습니다

책 이후 새로 생긴 컨디션들입니다.

| type | 의미 | 관련 |
| :--- | :--- | :--- |
| `PodReadyToStartContainers` | 샌드박스와 네트워크 준비 완료 | 1.29 이후 |
| `PodResizePending` | 자원 조정 요청을 아직 처리 못 함 | In-Place Resize |
| `PodResizeInProgress` | 자원 조정 적용 중 | In-Place Resize |
| `DisruptionTarget` | 축출(eviction) 대상으로 지정됨 | 노드 축소, 선점 등 |

`PodResize*` 두 가지는 [4.2절](<../04장. 파드로 애플리케이션 실행하기/4.2 YAML로 파드 만들기.md>)의 **재시작 없는 자원 조정**과 연결됩니다.

### 3) 노드 컨디션 정리

책에 나오는 `OutOfDisk` 컨디션은 **제거되었습니다.** 지금은 `DiskPressure`가 그 역할을 합니다.

### 4) `kubectl debug`로 더 깊이 조사할 수 있습니다

`exec`로 들어갈 수 없는 컨테이너(셸이 없는 distroless 이미지 등)도 조사할 수 있습니다.

```bash
# 문제 파드에 임시 컨테이너 붙이기
kubectl debug -it kiada --image=busybox --target=kiada

# 파드를 복제해서 명령을 바꿔 실행 (원본은 그대로 둠)
kubectl debug kiada -it --copy-to=kiada-debug --container=kiada -- sh

# 노드 자체를 조사
kubectl debug node/kiada-worker -it --image=busybox
```

`CrashLoopBackOff` 파드처럼 **셸을 띄울 틈도 없이 죽는 경우** `--copy-to`가 특히 유용합니다.

참고: <https://kubernetes.io/docs/tasks/debug/debug-application/debug-running-pod/>
