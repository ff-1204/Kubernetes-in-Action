# 4.3 파드와 상호작용하기

파드를 만들었으니 이제 접속하고, 로그를 보고, 안에 들어가 봅니다. **실무에서 가장 자주 쓰게 될 명령들**입니다.

## 파드에 요청 보내기

파드 IP는 클러스터 내부 전용이라 밖에서 직접 접근할 수 없습니다. 확인용으로 쓸 방법이 두 가지 있습니다.

> **밖으로 제대로 노출하는 방법은 11장 서비스에서 다룹니다.** 여기서는 "잘 떠 있는지 확인"하는 용도만 봅니다.

### 방법 1: 클러스터 안에서 요청하기

임시 파드를 하나 띄워서 안에서 요청합니다. **실제 파드끼리의 통신을 그대로 재현**하는 방식이라 더 현실적입니다.

```bash
kubectl run -it --rm test --image=busybox --restart=Never -- \
  wget -qO- 10.244.1.5:8080
```

| 옵션 | 의미 |
| :--- | :--- |
| `-it` | 터미널 연결 |
| `--rm` | 끝나면 파드 자동 삭제 |
| `--restart=Never` | 파드로 만들기(Job이 아니라) |
| `--` | 뒤는 컨테이너에서 실행할 명령 |

### 방법 2: API 서버를 통한 프록시

```bash
kubectl proxy
curl localhost:8001/api/v1/namespaces/default/pods/kiada/proxy/
```

## 로그 확인하기

가장 자주 쓰는 명령입니다.

```bash
kubectl logs kiada                    # 전체 로그
kubectl logs kiada -f                 # 실시간 추적 (follow)
kubectl logs kiada --tail=20          # 마지막 20줄
kubectl logs kiada --since=1h         # 최근 1시간
kubectl logs kiada --timestamps       # 시간 표시
kubectl logs kiada -c 컨테이너이름      # 컨테이너 지정 (다중 컨테이너 파드)
kubectl logs kiada --previous         # 재시작 전 컨테이너의 로그
kubectl logs -l app=kiada             # 레이블로 여러 파드 로그 한꺼번에
```

### `--previous`가 왜 중요할까요?

컨테이너가 죽고 다시 시작되면 **새 컨테이너의 로그만 보입니다.** 정작 원인이 담긴 죽기 직전 로그는 안 보입니다.

```bash
kubectl logs kiada              # 지금 도는 컨테이너 (아직 아무 로그 없음)
kubectl logs kiada --previous   # 죽기 직전 로그 <- 여기 원인이 있음!
```

`CrashLoopBackOff` 상태를 만나면 **반드시 `--previous`를 쓰세요.**

### 로그는 어디에 저장될까요?

컨테이너가 **표준 출력(stdout)과 표준 에러(stderr)** 로 뱉은 내용을 노드가 파일로 모아 둡니다.

```
/var/log/pods/<네임스페이스>_<파드이름>_<UID>/<컨테이너>/0.log
```

> **중요: 앱은 파일이 아니라 표준 출력으로 로그를 남겨야 합니다.**
> 컨테이너 안의 파일에 로그를 쓰면 컨테이너가 죽는 순간 함께 사라지고, `kubectl logs`로도 안 보입니다. 컨테이너 앱의 기본 원칙입니다.
>
> 그리고 로그는 **파드가 삭제되면 함께 사라집니다.** 그래서 실무에서는 Loki, Elasticsearch 같은 곳으로 따로 수집합니다.

## 컨테이너 안에서 명령 실행하기

```bash
kubectl exec kiada -- ls /                 # 단일 명령
kubectl exec -it kiada -- sh               # 대화형 셸
kubectl exec -it kiada -- bash             # bash가 있는 이미지라면
kubectl exec -it kiada -c 컨테이너이름 -- sh  # 컨테이너 지정
```

> **`--` 를 빼먹지 마세요.**
> ```bash
> kubectl exec kiada ls -l        # X: -l 을 kubectl이 가져감
> kubectl exec kiada -- ls -l     # O
> ```

### 안에 들어가서 할 만한 일

```bash
/ # env                       # 환경 변수 확인
/ # cat /etc/hosts            # 호스트 파일
/ # nslookup kubernetes       # DNS가 되는지
/ # wget -qO- localhost:8080  # 앱이 실제로 응답하는지
/ # ps aux                    # 프로세스 목록
/ # df -h                     # 디스크 사용량
/ # cat /etc/resolv.conf      # DNS 설정
```

**앱이 이상할 때, 밖에서 추측하지 말고 안에 들어가서 직접 확인하는 것이 가장 빠릅니다.**

### 셸이 없는 이미지라면?

`distroless`나 `scratch` 기반 이미지에는 `sh`조차 없습니다. `kubectl exec`가 실패합니다.

```
OCI runtime exec failed: exec: "sh": executable file not found in $PATH
```

이럴 때는 **`kubectl debug`** 를 씁니다. 임시 컨테이너를 파드에 붙여 줍니다.

```bash
kubectl debug -it kiada --image=busybox --target=kiada
```

`--target=kiada`를 주면 **kiada 컨테이너의 프로세스 네임스페이스를 공유**해서, 임시 컨테이너에서 kiada의 프로세스와 파일 시스템을 들여다볼 수 있습니다.

## 파일 복사하기

```bash
kubectl cp kiada:/app.js ./app.js          # 파드 -> 로컬
kubectl cp ./config.json kiada:/config.json  # 로컬 -> 파드
kubectl cp ./data kiada:/data -c 컨테이너이름  # 컨테이너 지정
```

파드 안에 `tar` 명령이 있어야 동작합니다. 없으면 실패합니다.

> **주의**: 파드에 파일을 직접 복사해 넣는 것은 **디버깅용으로만** 쓰세요. 파드가 재시작되면 사라집니다. 설정 파일은 ConfigMap(8장), 데이터는 볼륨(9~10장)으로 관리해야 합니다.

## 컨테이너에 붙기 (attach)

```bash
kubectl attach -it kiada
```

`exec`와 다릅니다.

| | `exec` | `attach` |
| :--- | :--- | :--- |
| 동작 | **새 프로세스**를 실행 | **기존 1번 프로세스**에 연결 |
| 용도 | 셸을 띄워 조사 | 앱의 표준 입출력에 직접 연결 |
| 위험도 | 안전 | **Ctrl+C 누르면 앱이 죽을 수 있음** |

`attach`는 위험하니 특별한 이유가 없으면 `exec`를 쓰세요.

## 파드 감시하기

```bash
kubectl get pods -w                    # 상태 변화 실시간 출력
kubectl get pods --watch-only          # 변화만
```

파드를 만들거나 지울 때 `-w`로 켜 두면 상태가 어떻게 바뀌는지 눈으로 볼 수 있습니다.

```
kiada   0/1   Pending             0s
kiada   0/1   ContainerCreating   1s
kiada   1/1   Running             5s
```

## 요약 및 비유

| 명령 | 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **logs** | 일지를 읽어 보기 | 컨테이너 표준 출력 조회 |
| **logs --previous** | 사고 직전 블랙박스 | 재시작 전 컨테이너 로그 |
| **exec** | 교실에 들어가 살펴보기 | 컨테이너에서 새 명령 실행 |
| **debug** | 조사관을 옆에 파견 | 임시 컨테이너를 붙여 조사 |
| **cp** | 서류를 건네주기 | 파일 복사 (임시 용도만) |
| **attach** | 진행 중인 통화에 끼어들기 | 기존 1번 프로세스에 연결 |

## 결론

* 파드 IP는 클러스터 내부 전용입니다. 여기서는 확인용으로만 접근하고, **밖으로 노출하는 것은 11장 서비스**에서 다룹니다.
* `CrashLoopBackOff`를 만나면 **반드시 `kubectl logs --previous`** 를 확인하세요.
* 앱 로그는 파일이 아니라 **표준 출력(stdout)** 으로 남겨야 합니다.
* `kubectl exec` 사용 시 **`--` 구분자**를 꼭 넣으세요.
* 셸이 없는 이미지는 **`kubectl debug`** 로 조사합니다.
* 파드에 파일을 직접 넣는 것은 임시방편일 뿐, 재시작되면 사라집니다.

## 공식 문서 업데이트 (2026년 8월 기준)

### 1) `kubectl exec`의 `--` 구분자가 필수가 되었습니다

책이나 옛 자료에는 이런 형태가 나옵니다.

```bash
kubectl exec kiada -it sh          # 옛 문법. 경고가 뜨거나 동작하지 않음
```

지금은 반드시 이렇게 씁니다.

```bash
kubectl exec -it kiada -- sh
```

### 2) `kubectl debug`가 크게 강화되었습니다

책 출간 시점에는 임시 컨테이너(Ephemeral Container)가 알파 기능이었지만, 지금은 정식 기능이고 활용법도 늘었습니다.

```bash
# 실행 중인 파드에 조사용 컨테이너 붙이기
kubectl debug -it kiada --image=busybox --target=kiada

# 파드를 복사해서 명령만 바꿔 띄우기 (CrashLoopBackOff 조사에 최적)
kubectl debug kiada -it --copy-to=kiada-debug --container=kiada -- sh

# 이미지만 바꿔서 복사본 띄우기
kubectl debug kiada --copy-to=kiada-debug --set-image=kiada=busybox

# 노드 자체를 조사
kubectl debug node/kiada-worker -it --image=busybox
```

**`--copy-to`가 특히 유용합니다.** 계속 죽는 파드는 셸을 띄울 틈도 없는데, 복사본의 명령을 `sleep 3600`으로 바꿔 띄우면 느긋하게 조사할 수 있습니다.

참고: <https://kubernetes.io/docs/tasks/debug/debug-application/debug-running-pod/>

### 3) `kubectl logs`에 옵션이 추가되었습니다

```bash
kubectl logs -l app=kiada --max-log-requests=10   # 레이블 매칭 파드 여러 개
kubectl logs kiada --all-containers=true          # 모든 컨테이너 로그 한꺼번에
kubectl logs deployment/kiada                     # 디플로이먼트 단위로
```
