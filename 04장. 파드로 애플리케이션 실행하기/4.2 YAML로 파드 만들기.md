# 4.2 YAML로 파드 만들기

이제 직접 파드 매니페스트를 작성해 봅니다.

## 가장 단순한 파드

**kiada.yaml**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kiada
spec:
  containers:
    - name: kiada
      image: luksa/kiada:0.1
      ports:
        - name: http
          containerPort: 8080
```

```bash
kubectl apply -f kiada.yaml
kubectl get pods
# NAME    READY   STATUS    RESTARTS   AGE
# kiada   1/1     Running   0          10s
```

### `ports`는 사실 필수가 아닙니다

놀랍게도 `ports` 항목을 빼도 앱은 정상 동작합니다. 컨테이너가 8080에서 듣고 있다면 `ports`에 안 적어도 접근됩니다.

**그럼 왜 적을까요?**

* **문서화**: 이 파드가 어떤 포트를 쓰는지 다른 사람에게 알려 줍니다
* **이름 부여**: `name: http` 로 이름을 붙이면 서비스에서 숫자 대신 이름으로 참조할 수 있습니다

```yaml
# 서비스에서
ports:
  - port: 80
    targetPort: http      # 8080 대신 이름으로!
```

포트 번호를 바꿔도 서비스 YAML은 안 고쳐도 되니 편리합니다. **적는 습관을 들이는 게 좋습니다.**

## YAML 초안을 자동으로 만들기

손으로 처음부터 쓰는 것보다 훨씬 빠른 방법입니다.

```bash
kubectl run kiada --image=luksa/kiada:0.1 \
  --port=8080 --dry-run=client -o yaml > kiada.yaml
```

실제로 만들지는 않고 YAML만 출력해 줍니다. 이걸 받아서 필요한 부분만 고치면 됩니다.

## 자주 쓰는 spec 필드들

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kiada
  labels:
    app: kiada
spec:
  containers:
    - name: kiada
      image: luksa/kiada:0.1
      imagePullPolicy: IfNotPresent

      ports:
        - name: http
          containerPort: 8080

      env:                              # 환경 변수
        - name: APP_MODE
          value: "production"

      command: ["node"]                 # ENTRYPOINT 덮어쓰기
      args: ["/app.js"]                 # CMD 덮어쓰기

      resources:                        # 자원 요청과 제한
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          cpu: 500m
          memory: 256Mi

      volumeMounts:                     # 볼륨 연결
        - name: data
          mountPath: /data

  volumes:                              # 볼륨 정의
    - name: data
      emptyDir: {}

  restartPolicy: Always                 # 재시작 정책
  nodeSelector:                         # 노드 선택
    disktype: ssd
```

### imagePullPolicy — 이미지를 언제 새로 받을까

| 값 | 동작 |
| :--- | :--- |
| `Always` | 매번 레지스트리에서 확인 |
| `IfNotPresent` | 로컬에 없을 때만 받음 |
| `Never` | 절대 안 받음. 로컬에만 의존 |

**기본값 규칙이 함정입니다.**

* 태그가 `latest`이거나 태그가 없으면 → `Always`
* 그 외 명시적 태그면 → `IfNotPresent`

그래서 `myapp:1.0` 이미지를 고쳐서 다시 push해도 **클러스터가 옛 이미지를 계속 씁니다.** 개발 중에 "왜 코드 수정이 반영이 안 되지?" 하는 원인 1위입니다. 태그를 매번 바꾸는 것이 정답입니다.

### command와 args

Dockerfile의 `ENTRYPOINT`/`CMD`를 덮어쓰는 필드입니다.

| Dockerfile | 파드 YAML |
| :--- | :--- |
| `ENTRYPOINT` | `command` |
| `CMD` | `args` |

```yaml
# 디버깅용으로 앱 대신 셸을 띄우고 싶을 때
command: ["sh"]
args: ["-c", "sleep 3600"]
```

컨테이너가 계속 죽을 때, 이렇게 바꿔서 띄워 놓고 안에 들어가 조사하는 기법을 자주 씁니다.

### resources — 매우 중요합니다

```yaml
resources:
  requests:        # 최소 보장. 스케줄러가 이 값으로 노드를 고름
    cpu: 100m      # 100 밀리코어 = 0.1 코어
    memory: 128Mi
  limits:          # 최대 한도. 넘으면 제재
    cpu: 500m
    memory: 256Mi
```

| | requests | limits |
| :--- | :--- | :--- |
| 의미 | **최소한 이만큼은 보장해 줘** | **이 이상은 못 써** |
| 쓰는 곳 | 스케줄러의 노드 선택 기준 | kubelet/cgroups의 실제 제한 |
| CPU 초과 시 | — | **느려짐** (스로틀링) |
| 메모리 초과 시 | — | **강제 종료** (OOMKilled) |

> **단위 읽는 법**
> * CPU: `1` = 1코어, `500m` = 0.5코어, `100m` = 0.1코어 (m = 밀리)
> * 메모리: `Mi` = 메비바이트(1024 기반), `M` = 메가바이트(1000 기반). 보통 `Mi`를 씁니다

**requests를 안 적으면 어떻게 될까요?** 스케줄러가 이 파드가 얼마나 쓸지 몰라서, 이미 꽉 찬 노드에 밀어 넣을 수 있습니다. 그러면 노드 전체가 불안정해집니다. **실무에서 requests는 사실상 필수입니다.**

### QoS 등급

requests와 limits를 어떻게 적었느냐에 따라 파드에 등급이 매겨집니다. 노드에 메모리가 부족해지면 **등급이 낮은 파드부터 쫓겨납니다.**

| 등급 | 조건 | 축출 순서 |
| :--- | :--- | :--- |
| **Guaranteed** | requests = limits (모든 컨테이너) | 가장 나중 |
| **Burstable** | requests < limits | 중간 |
| **BestEffort** | 아무것도 안 적음 | **가장 먼저 쫓겨남** |

```bash
kubectl get pod kiada -o jsonpath='{.status.qosClass}'
```

중요한 앱이라면 `requests = limits`로 맞춰서 **Guaranteed** 등급을 받게 하세요.

### restartPolicy

| 값 | 동작 |
| :--- | :--- |
| `Always` | 항상 재시작 (기본값) |
| `OnFailure` | 실패했을 때만 재시작 |
| `Never` | 재시작 안 함 |

**주의**: 이것은 **파드 안의 컨테이너**를 재시작하는 정책입니다. 파드 자체를 되살리는 게 아닙니다.

재시작이 반복되면 대기 시간이 점점 늘어납니다. 10초 → 20초 → 40초 → ... → 최대 5분. 이 상태가 바로 `CrashLoopBackOff`입니다.

## 만든 파드 확인하기

```bash
kubectl get pod kiada -o yaml           # 전체 매니페스트
kubectl describe pod kiada              # 사람이 읽기 좋게
kubectl get pod kiada -o wide           # IP와 노드
kubectl get pod kiada -o jsonpath='{.status.podIP}'
```

## 요약 및 비유

| 필드 | 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **image** | 어떤 밀키트를 쓸지 | 실행할 컨테이너 이미지 |
| **imagePullPolicy** | 매번 새로 사올지 여부 | 이미지 다운로드 정책 |
| **command / args** | 조리법을 바꿔 쓰기 | ENTRYPOINT/CMD 덮어쓰기 |
| **requests** | 예약해 둔 좌석 수 | 최소 보장 자원 (스케줄링 기준) |
| **limits** | 넘으면 안 되는 한도 | 최대 사용 가능 자원 |
| **QoS 등급** | 좌석 등급 (일등석/일반석) | 자원 부족 시 축출 우선순위 |
| **restartPolicy** | 넘어지면 다시 일으킬지 | 컨테이너 재시작 정책 |

## 결론

* 파드 YAML의 뼈대는 **`apiVersion` / `kind` / `metadata` / `spec.containers`** 입니다.
* `ports`는 필수가 아니지만 **문서화와 이름 참조**를 위해 적는 것이 좋습니다.
* **명시적 태그를 쓰면 `imagePullPolicy`가 `IfNotPresent`** 가 되어 이미지가 갱신되지 않습니다. 태그를 매번 바꾸세요.
* **`requests`는 스케줄러의 기준, `limits`는 실제 제한**입니다. 메모리 초과는 즉시 강제 종료입니다.
* `requests = limits`로 맞추면 **Guaranteed** 등급을 받아 가장 안전합니다.
* `kubectl run --dry-run=client -o yaml`로 초안을 만들면 시간을 크게 아낍니다.

## 공식 문서 업데이트 (2026년 8월 기준)

### 1) 자원을 재시작 없이 바꿀 수 있습니다

책에서는 `resources`를 바꾸려면 반드시 파드를 다시 만들어야 했습니다. **1.35부터 In-Place Pod Resize가 정식 기능**이 되어 재시작 없이 조정할 수 있습니다.

```yaml
spec:
  containers:
    - name: kiada
      resizePolicy:
        - resourceName: cpu
          restartPolicy: NotRequired       # CPU는 재시작 없이
        - resourceName: memory
          restartPolicy: RestartContainer  # 메모리는 재시작 후
```

```bash
kubectl patch pod kiada --subresource=resize -p \
  '{"spec":{"containers":[{"name":"kiada","resources":{"requests":{"cpu":"200m"}}}]}}'
```

제약: **CPU와 메모리만** 가능, **QoS 등급은 변경 불가**, 윈도우 미지원, init/임시 컨테이너 불가.

참고: <https://kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/>

### 2) 파드 단위 자원 지정이 가능해졌습니다

컨테이너마다 적는 대신 파드 전체에 지정할 수 있습니다. 사이드카가 여럿일 때 특히 편합니다.

```yaml
spec:
  resources:
    limits:
      cpu: "1"
      memory: 512Mi
  containers:
    - name: kiada
      image: luksa/kiada:0.1
```

### 3) `securityContext` 설정이 사실상 필수가 되었습니다

Pod Security Admission의 `restricted` 정책을 적용한 네임스페이스에서는 아래 설정이 없으면 **파드 생성 자체가 거부됩니다.** 실무 클러스터에서는 대부분 켜져 있습니다.

```yaml
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: kiada
      image: luksa/kiada:0.1
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
        readOnlyRootFilesystem: true
```

책의 예제 YAML을 실무 클러스터에 그대로 올리면 거부당할 수 있으니 기억해 두세요.

### 4) 이미지 볼륨(Image Volume)

컨테이너 이미지를 **볼륨처럼 마운트**하는 기능이 추가되었습니다. AI 모델 파일이나 대용량 데이터셋을 이미지로 배포할 때 유용합니다.

```yaml
volumes:
  - name: model
    image:
      reference: myregistry/llm-model:v1
      pullPolicy: IfNotPresent
```

### 5) `kubectl run`은 파드 하나만 만듭니다

옛 자료의 `kubectl run --replicas=3`은 **동작하지 않습니다.** 지금 `kubectl run`은 순수하게 **파드 하나만** 만듭니다. 이 장의 실습에는 오히려 딱 맞습니다.
