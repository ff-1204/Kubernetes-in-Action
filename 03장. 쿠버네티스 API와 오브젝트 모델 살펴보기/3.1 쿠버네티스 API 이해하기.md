# 3.1 쿠버네티스 API 이해하기

쿠버네티스에서 하는 모든 일은 **API를 통해 객체(Object)를 만들고 고치고 지우는 것**입니다. 이 원리를 이해하면 쿠버네티스 전체가 훨씬 쉬워집니다.

> "쿠버네티스 API"는 kube-apiserver와 같은 말이 아닙니다. 이 절에서 "API"는 **인터페이스**를 가리킵니다.

## 쿠버네티스는 거대한 데이터베이스입니다

조금 과감하게 표현하면 이렇습니다.

> **쿠버네티스 = "객체를 저장하는 데이터베이스" + "그 객체를 실현하려고 애쓰는 컨트롤러들"**

사용자가 하는 일은 **"이런 객체가 있어야 해"라고 등록하는 것.** 그 뒤는 컨트롤러들이 알아서 현실로 만듭니다.

```mermaid
graph LR
    U["사용자<br/><i>Pod 객체를 하나 등록할게</i>"] --> A["API 서버"]
    A --> E["etcd에 저장"]
    E --> C["컨트롤러들<br/>이걸 보고 실제로 만들어 냄"]
```

## RESTful API

쿠버네티스 API는 웹 개발에서 쓰는 REST 규칙을 그대로 따릅니다.

| HTTP 메서드 | 하는 일 | kubectl 명령 |
| :--- | :--- | :--- |
| `GET` | 조회 | `kubectl get` |
| `POST` | 생성 | `kubectl create` |
| `PUT` / `PATCH` | 수정 | `kubectl apply`, `kubectl edit` |
| `DELETE` | 삭제 | `kubectl delete` |

URL 형태도 규칙적입니다.

```
/api/v1/namespaces/{네임스페이스}/pods/{이름}
/apis/apps/v1/namespaces/{네임스페이스}/deployments/{이름}
```

### 직접 API를 호출해 보기

`kubectl proxy`를 쓰면 인증을 대신 처리해 주는 통로가 열립니다.

```bash
kubectl proxy
# Starting to serve on 127.0.0.1:8001
```

다른 터미널에서:

```bash
curl http://localhost:8001/api/v1/namespaces/default/pods
curl http://localhost:8001/api/v1/nodes
```

**kubectl 없이도 쿠버네티스를 쓸 수 있다**는 사실이 눈으로 확인됩니다. kubectl은 그저 이 요청을 편하게 만들어 주는 껍데기입니다.

`-v=8` 을 붙이면 kubectl이 보내는 요청이 그대로 보입니다. 방금 `curl` 로 호출한 것과 같은 주소입니다.

```bash
kubectl get pods -v=8
# GET https://127.0.0.1:6443/api/v1/namespaces/default/pods?limit=500
```

> **모든 kubectl 명령은 결국 API 요청 하나로 바뀝니다.** 명령의 형태도 항상 `kubectl [동작] [리소스종류] [이름] [옵션]` 로, 위 URL 구조와 그대로 대응합니다. 실제 명령 사용법은 파드를 직접 만들어 보는 **4장**에서 익힙니다.

## 명령형 vs 선언형

같은 일을 시키는 방식이 두 가지입니다.

| | 명령형(Imperative) | 선언형(Declarative) |
| :--- | :--- | :--- |
| 예 | `kubectl create deployment ...` | `kubectl apply -f app.yaml` |
| 장점 | 빠르고 간단 | **YAML을 Git에 남길 수 있음**, 클러스터가 날아가도 복구 가능 |
| 단점 | **기록이 남지 않음** | 파일을 만들어야 함 |

**실무 표준은 선언형입니다.** 1.1절의 선언적 모델이 명령 수준에서 드러나는 지점입니다. 그래서 `create` 보다 **`apply`** 를 씁니다. `create` 는 이미 있으면 오류가 나지만 `apply` 는 알아서 생성/수정을 판단합니다.

## API 그룹과 버전

쿠버네티스에는 객체 종류가 수십 가지입니다. 이를 정리하기 위해 **그룹(Group)** 으로 나눕니다.

### 핵심 그룹 (Core / Legacy)

가장 기본이 되는 객체들로, **그룹 이름이 없습니다.**

```yaml
apiVersion: v1        # 그룹 없이 버전만
kind: Pod
```

여기 속하는 것: `Pod`, `Service`, `Node`, `Namespace`, `ConfigMap`, `Secret`, `PersistentVolume` 등

### 이름 있는 그룹 (Named Groups)

나중에 추가된 객체들은 그룹에 소속됩니다.

```yaml
apiVersion: apps/v1   # 그룹/버전
kind: Deployment
```

| 그룹 | 주요 객체 |
| :--- | :--- |
| `apps` | Deployment, ReplicaSet, StatefulSet, DaemonSet |
| `batch` | Job, CronJob |
| `networking.k8s.io` | Ingress, NetworkPolicy |
| `storage.k8s.io` | StorageClass, CSIDriver |
| `rbac.authorization.k8s.io` | Role, RoleBinding |
| `autoscaling` | HorizontalPodAutoscaler |
| `gateway.networking.k8s.io` | Gateway, HTTPRoute |

> **왜 이렇게 나눴을까요?**
> 그룹마다 **독립적으로 버전을 올릴 수 있게** 하기 위해서입니다. `apps` 그룹이 v2로 올라가도 `batch` 그룹은 v1 그대로 둘 수 있습니다.

### 버전의 의미

| 버전 | 안정성 | 의미 |
| :--- | :--- | :--- |
| `v1alpha1` | 낮음 | 실험 단계. **예고 없이 사라질 수 있음**. 기본적으로 꺼져 있음 |
| `v1beta1` | 보통 | 꽤 쓸 만함. 하지만 **필드 이름이 바뀔 수 있음** |
| `v1` | 높음 | 정식(GA). **하위 호환이 보장됨** |

> **실무 규칙: 운영 환경에서는 정식 버전(`v1`)만 쓰세요.**
> beta API를 썼다가 쿠버네티스를 업그레이드하는 순간 전부 깨지는 사고가 실제로 자주 일어납니다.

### 사용 가능한 것 확인하기

```bash
kubectl api-versions      # 사용 가능한 그룹/버전 목록
kubectl api-resources     # 객체 종류 전체 목록
```

```bash
kubectl api-resources | head
# NAME          SHORTNAMES   APIVERSION   NAMESPACED   KIND
# pods          po           v1           true         Pod
# services      svc          v1           true         Service
# nodes         no           v1           false        Node
# deployments   deploy       apps/v1      true         Deployment
```

`NAMESPACED` 열을 눈여겨보세요. `true`면 네임스페이스에 속하고, `false`면 클러스터 전체에 하나뿐인 객체입니다.

## 여기서 멈추고, 나중에 이어지는 것

API의 두 가지 성질은 개념만 기억해 두고 넘어갑니다.

* **객체마다 소속이 다릅니다.** 파드처럼 네임스페이스에 속하는 것이 있고, 노드처럼 클러스터 전체에 하나뿐인 것이 있습니다. 위 `NAMESPACED` 열이 그 구분입니다. → **7장**
* **API는 사용자가 늘릴 수 있습니다.** **CRD(CustomResourceDefinition)** 를 등록하면 쿠버네티스 기본에 없는 객체 종류를 만들 수 있습니다. 쿠버네티스가 도구가 아니라 플랫폼으로 불리는 이유입니다. → **16장 오퍼레이터**

## 요약 및 비유

| 개념 | 도서관 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **API 서버** | 도서관 대출 창구 | 모든 요청을 처리하는 단일 진입점 |
| **kubectl** | 창구에 내미는 신청서 양식 | API 요청을 대신 만들어 주는 CLI |
| **객체(Object)** | 책 한 권 | 클러스터에 등록되는 하나의 항목 |
| **API 그룹** | 문학 / 과학 / 역사 서가 | 관련 객체들의 묶음 |
| **버전(v1, beta)** | 초판 / 개정판 | 안정성 단계 표시 |
| **네임스페이스** | 층별 구역 | 객체를 논리적으로 나누는 공간 |

## 결론

* 쿠버네티스로 하는 모든 작업은 결국 **API 객체를 CRUD 하는 것**이고, **kubectl은 그 요청을 만들어 주는 클라이언트**일 뿐입니다. `-v=8`로 직접 확인할 수 있습니다.
* 실무 표준은 **선언형(`apply` + YAML + Git)** 입니다. 명령형은 빠르지만 기록이 남지 않습니다.
* API는 **그룹 + 버전**으로 정리되며, `apiVersion` 필드에 그 조합을 적습니다.
* **`v1`(정식)만 운영에 쓰고, alpha/beta는 학습·실험용**으로 제한하세요.
* 객체가 **네임스페이스 소속인지 클러스터 전역인지**(7장), **CRD로 API를 늘릴 수 있다는 것**(16장)은 개념만 잡고 넘어갑니다.

## 공식 문서 업데이트 (2026년 8월 기준)

### 1) 제거된 API 버전들 (옛 자료를 볼 때 주의)

인터넷의 오래된 YAML을 그대로 쓰면 오류가 납니다. 대표적인 변경입니다.

| 객체 | 제거된 버전 | 제거 시점 | 지금 써야 할 버전 |
| :--- | :--- | :--- | :--- |
| CronJob | `batch/v1beta1` | 1.25 | `batch/v1` |
| PodDisruptionBudget | `policy/v1beta1` | 1.25 | `policy/v1` |
| PodSecurityPolicy | `policy/v1beta1` | 1.25 | **제거됨** (PSA로 대체) |
| HorizontalPodAutoscaler | `autoscaling/v2beta2` | 1.26 | `autoscaling/v2` |
| CSIStorageCapacity | `storage.k8s.io/v1beta1` | 1.27 | `storage.k8s.io/v1` |
| Ingress | `extensions/v1beta1` | 1.22 | `networking.k8s.io/v1` |

전체 목록: <https://kubernetes.io/docs/reference/using-api/deprecation-guide/>

내 클러스터에서 문제 되는 것을 찾으려면 **kubent(kube-no-trouble)** 같은 도구를 씁니다.

### 2) Gateway API는 CRD로 제공됩니다

13장에서 배울 Gateway API는 쿠버네티스에 **기본 내장되어 있지 않습니다.** CRD를 따로 설치해야 합니다.

```bash
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.0/standard-install.yaml
kubectl get crds | grep gateway
```

이것이 바로 "CRD로 API를 확장한다"는 개념의 가장 대표적인 실제 사례입니다.

### 3) Server-Side Apply가 기본입니다

여러 사람이나 도구가 같은 객체를 동시에 고칠 때 충돌을 관리하는 방식이 개선되었습니다. 객체를 조회하면 `metadata.managedFields`라는 낯선 필드가 보이는데, **"이 필드는 누가 관리하는가"를 기록한 것**입니다.

```bash
kubectl get pod kiada -o yaml --show-managed-fields=false   # 지저분하면 숨기기
```

참고: <https://kubernetes.io/docs/reference/using-api/server-side-apply/>

### 4) `--dry-run` 은 값을 반드시 명시해야 합니다

옛 자료의 `--dry-run=true` 나 값 없는 `--dry-run` 은 **더 이상 동작하지 않습니다.**

```bash
--dry-run=client    # 서버에 보내지 않고 로컬에서만 처리
--dry-run=server    # 서버가 검증까지 하되 저장은 하지 않음
```
