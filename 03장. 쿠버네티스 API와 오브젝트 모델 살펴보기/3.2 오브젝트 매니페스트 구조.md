# 3.2 오브젝트 매니페스트 구조

**매니페스트(Manifest)** 는 "이런 객체를 만들어 줘"라고 적은 YAML(또는 JSON) 파일입니다. 쿠버네티스 객체는 종류가 달라도 **구조가 항상 똑같습니다.** 이 구조 하나만 외우면 모든 객체를 읽을 수 있습니다.

## 모든 객체의 공통 4구조

```yaml
apiVersion: v1        # 1. 어떤 API 버전을 쓸 것인가
kind: Pod             # 2. 어떤 종류의 객체를 만들 것인가
metadata:             # 3. 이름표와 꼬리표
  name: kiada
spec:                 # 4. 원하는 상태 (내가 작성)
  containers:
    - name: kiada
      image: luksa/kiada:0.1
status:               # 5. 실제 상태 (쿠버네티스가 채움 - 내가 쓰지 않음)
  phase: Running
```

> **핵심 한 줄**
> **`spec`은 내가 쓰고, `status`는 쿠버네티스가 씁니다.**
> 컨트롤러가 하는 일은 결국 `status`를 `spec`에 맞추는 것입니다. 1.1절의 조정 루프가 여기서 구체화됩니다.

## 1. apiVersion

어떤 API 그룹과 버전을 쓸지 지정합니다.

```yaml
apiVersion: v1              # 핵심 그룹 (Pod, Service 등)
apiVersion: apps/v1         # apps 그룹 (Deployment 등)
apiVersion: batch/v1        # batch 그룹 (Job 등)
```

틀리면 이런 오류가 납니다.

```
error: unable to recognize "app.yaml": no matches for kind "Deployment" in version "v1"
```

`kubectl explain deployment`로 올바른 버전을 확인할 수 있습니다.

## 2. kind

만들 객체의 종류입니다. **반드시 대문자로 시작**합니다.

```yaml
kind: Pod            # O
kind: pod            # X 오류
kind: Deployment     # O
```

## 3. metadata

객체를 식별하는 정보입니다.

```yaml
metadata:
  name: kiada                    # 이름 (필수)
  namespace: default             # 소속 네임스페이스
  labels:                        # 레이블 - 선택과 그룹핑용
    app: kiada
    version: "0.1"
    tier: frontend
  annotations:                   # 어노테이션 - 부가 정보 기록용
    description: "첫 번째 실습 앱"
    kubernetes.io/change-cause: "v0.1 최초 배포"
```

### 레이블 vs 어노테이션 (자주 헷갈립니다)

| | 레이블(labels) | 어노테이션(annotations) |
| :--- | :--- | :--- |
| 목적 | **선택하고 그룹 짓기** | **정보를 기록해 두기** |
| 검색 | `kubectl get -l app=kiada` 가능 | 검색 불가 |
| 길이 제한 | 63자 | **사실상 무제한** |
| 쓰는 곳 | 서비스가 파드를 고를 때, 셀렉터 | 도구가 남기는 메타정보, 설명 |

```bash
kubectl get pods -l app=kiada           # 레이블로 검색
kubectl get pods -l 'version in (0.1,0.2)'
kubectl get pods --show-labels
```

**서비스가 어떤 파드로 요청을 보낼지 고르는 기준이 바로 레이블입니다.** 7장에서 자세히 다룹니다.

### 이름 규칙

* 소문자, 숫자, `-`, `.` 만 사용 가능
* 253자 이하
* 같은 네임스페이스 안에서 같은 종류끼리는 이름이 중복될 수 없음

```yaml
name: kiada-front       # O
name: Kiada_Front       # X 대문자와 언더스코어 불가
```

### 자동으로 채워지는 metadata 필드

객체를 만들면 쿠버네티스가 알아서 추가하는 필드들입니다.

```yaml
metadata:
  uid: 7d4c8f9b-6d3e-4a1b-9c2d-8e7f6a5b4c3d   # 전 우주에서 유일한 ID
  resourceVersion: "12345"                     # 수정될 때마다 증가
  creationTimestamp: "2026-08-19T10:30:00Z"
  generation: 1
```

* **uid**: 같은 이름으로 지웠다 다시 만들어도 uid는 달라집니다. 쿠버네티스는 이름이 아니라 uid로 객체를 구분합니다.
* **resourceVersion**: 낙관적 잠금(optimistic locking)에 쓰입니다. 두 사람이 동시에 같은 객체를 고치면 나중 사람이 충돌 오류를 받습니다.

## 4. spec — 내가 원하는 상태

객체 종류마다 내용이 완전히 다릅니다. 진짜 알맹이가 들어가는 곳입니다.

**Pod의 spec**

```yaml
spec:
  containers:
    - name: kiada
      image: luksa/kiada:0.1
      ports:
        - containerPort: 8080
      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          cpu: 500m
          memory: 256Mi
```

**Deployment의 spec** — 안에 파드 템플릿이 통째로 들어갑니다

```yaml
spec:
  replicas: 3
  selector:
    matchLabels:
      app: kiada
  template:              # <-- 여기부터가 파드의 설계도
    metadata:
      labels:
        app: kiada
    spec:
      containers:
        - name: kiada
          image: luksa/kiada:0.1
```

> **`template` 안쪽은 사실상 Pod 매니페스트입니다.**
> `apiVersion`과 `kind`만 빠져 있을 뿐, `metadata`와 `spec` 구조가 똑같습니다. 이 중첩 구조를 이해하면 Deployment YAML이 갑자기 쉬워집니다.
>
> 그리고 **`selector.matchLabels`와 `template.metadata.labels`는 반드시 일치해야 합니다.** 안 맞으면 디플로이먼트가 자기가 만든 파드를 못 찾아서 파드를 무한정 만들어 냅니다. 초보자가 가장 많이 겪는 오류입니다.

## 5. status — 실제 상태

쿠버네티스가 채우는 영역입니다. **YAML에 직접 쓰지 않습니다.**

```yaml
status:
  phase: Running
  podIP: 10.244.1.5
  hostIP: 172.18.0.3
  startTime: "2026-08-19T10:30:05Z"
  conditions:
    - type: Ready
      status: "True"
      lastTransitionTime: "2026-08-19T10:30:10Z"
  containerStatuses:
    - name: kiada
      ready: true
      restartCount: 0
      state:
        running:
          startedAt: "2026-08-19T10:30:08Z"
```

```bash
kubectl get pod kiada -o yaml       # spec + status 전부 보기
kubectl get pod kiada -o jsonpath='{.status.podIP}'   # 특정 값만 뽑기
```

## YAML 문법 주의사항

YAML은 사소한 실수로 오류가 잘 납니다.

### 들여쓰기는 반드시 스페이스

```yaml
spec:
  containers:      # 스페이스 2칸 (탭 사용 시 오류!)
    - name: kiada  # 리스트는 하이픈
```

**탭(Tab)을 쓰면 무조건 오류입니다.** 에디터 설정에서 탭을 스페이스로 바꿔 두세요.

### 따옴표가 필요한 경우

```yaml
version: 0.1        # 숫자 0.1 로 해석됨
version: "0.1"      # 문자열 "0.1" - 레이블 값은 반드시 문자열이어야 함

enabled: yes        # YAML 1.1에서 true 로 해석될 수 있음 (위험)
enabled: "yes"      # 안전
```

레이블 값은 **항상 문자열**이어야 하므로 숫자처럼 보이면 따옴표를 붙이세요.

### 여러 객체를 한 파일에

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kiada
spec:
  containers:
    - name: kiada
      image: luksa/kiada:0.1
---                     # 구분자
apiVersion: v1
kind: Service
metadata:
  name: kiada
spec:
  selector:
    app: kiada
  ports:
    - port: 8080
```

`---` 로 구분하면 한 파일에 여러 객체를 넣을 수 있습니다. `kubectl apply -f` 한 번에 전부 만들어집니다.

### 문법 검사

```bash
kubectl apply -f app.yaml --dry-run=server     # 서버에서 검증만
kubectl apply -f app.yaml --validate=strict    # 오타 필드까지 검사
```

`--validate=strict`가 특히 유용합니다. `contaienrs` 같은 오타를 잡아 줍니다.

## 요약 및 비유

| 필드 | 택배 송장 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **apiVersion** | 송장 양식 버전 | API 그룹과 버전 지정 |
| **kind** | 물품 종류 | 만들 객체의 타입 |
| **metadata.name** | 수취인 이름 | 객체 식별자 |
| **metadata.labels** | 분류 스티커 | 검색·선택용 키-값 |
| **metadata.annotations** | 배송 메모 | 검색 안 되는 부가 정보 |
| **spec** | 주문 내용 | 내가 원하는 상태 |
| **status** | 배송 현황 | 쿠버네티스가 기록한 실제 상태 |

---

## 결론

* 모든 쿠버네티스 객체는 **`apiVersion` / `kind` / `metadata` / `spec` / `status`** 구조를 공유합니다.
* **`spec`은 사람이 쓰고 `status`는 시스템이 씁니다.** 이 둘의 간극을 메우는 것이 컨트롤러의 일입니다.
* **레이블은 검색용, 어노테이션은 기록용**입니다.
* Deployment의 `template` 안쪽은 **Pod 매니페스트 그 자체**이며, `selector`와 레이블이 일치해야 합니다.
* YAML은 **탭 금지**, 레이블 값은 **따옴표로 문자열 처리**하는 습관을 들이세요.

## 공식 문서 업데이트 (2026년 8월 기준)

### 1) `metadata.managedFields`가 기본으로 붙습니다

객체를 `-o yaml`로 조회하면 책에는 없던 `managedFields`라는 긴 블록이 보입니다. **Server-Side Apply** 때문에 생긴 필드로, "이 필드는 kubectl이, 저 필드는 컨트롤러가 관리한다"를 기록한 것입니다.

읽기 불편하면 숨길 수 있습니다.

```bash
kubectl get pod kiada -o yaml --show-managed-fields=false
```

### 2) `--validate=strict`가 기본값이 되었습니다

예전에는 YAML에 없는 필드를 써도 조용히 무시했습니다. 지금은 기본적으로 **엄격 검증**이라 오타가 있으면 바로 오류가 납니다.

```
error: error validating "app.yaml": ValidationError(Pod.spec):
unknown field "contaienrs" in io.k8s.api.core.v1.PodSpec
```

**좋은 변화입니다.** 예전에는 오타 때문에 설정이 적용 안 된 걸 모르고 몇 시간씩 헤매는 일이 흔했습니다.

### 3) 기본 시크릿 토큰 자동 생성이 사라졌습니다

책에는 서비스어카운트를 만들면 토큰 Secret이 자동으로 생긴다고 나오지만, **1.24부터 자동 생성되지 않습니다.** 지금은 파드에 **수명이 정해진 토큰이 볼륨으로 자동 주입**되는 방식(Bound Service Account Token)을 씁니다.

토큰이 꼭 필요하면 직접 만들어야 합니다.

```bash
kubectl create token my-serviceaccount --duration=1h
```

### 4) 어노테이션 표준화

`kubectl.kubernetes.io/last-applied-configuration` 어노테이션은 Server-Side Apply를 쓰면 더 이상 생기지 않습니다. 예전 `kubectl apply`가 이전 상태를 비교하려고 통째로 저장하던 것인데, 이제 `managedFields`가 그 역할을 대신합니다.
